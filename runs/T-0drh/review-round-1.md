**1. `docs/spec/setup.md:98` and `:188-191` — the setup commits never reach the default branch.** Cited sentences: `setup.md:70` "a Git repository with the root commit on `main` and the setup commits on the branch `layup-setup`"; `setup.md:98` "Writes the push of `layup-setup` and the apply command to `commands.sh`"; `setup.md:188-191` "the push of the root commit (S03), of `layup-setup` (S13) and of `layup-records` (S15), and the apply of the default branch's ruleset (S13), in that order". Basis: no step pushes `layup-setup` onto the default branch or merges it. After `commands.sh`, the default branch holds the root commit only, under a ruleset that requires a pull request. The architecture puts the setup commits on the default branch: `architecture.md:405` "The Operator pushes the setup commits on top of the root commit", and `architecture.md:196-197` "The setup commits are allowed by their SHA" (as updates of the default branch). With the spec as written, `records.md:131-132` ("a target set up in phase 1 merges with LAYUP absent from the start") and the `REQ-002` criterion (a target that passes the discipline tests) do not hold for the default branch. One sentence fixes it: the S13 command pushes `layup-setup` to the default branch (for example `git push origin layup-setup:main`) before the ruleset applies. `material` (operative omission; contradicts §5 Scaffold 6).
