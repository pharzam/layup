## Verdict

Borrow the pattern. BMAD gives the best public specification chain we tested (PRD with `FR-N` and testable consequences, spec with `CAP-N` intent and success, architecture decisions `AD-n` that bind `CAP` ids, a ticket tree whose `covers` cites numbered source lines), and it keeps all of it as plain files in the project's Git. But every judgement in it is an LLM prompt, it has no rule protection, no telemetry, no escalation rule, and no check that a trace id resolves. It is Python and TOML, so LAYUP (Go standard library only) cannot use it as a library or read its TOML without a parser.

**S1 test (the two deliberate gaps).** Gap A is line 8, "fast on a large repository" (no measurement method). Gap B is line 9, "stale" (undefined term).

- Run 1 (PRD) found both, in one JSON batch: "OQ-1 (phase-blocker): What makes a TODO stale ...? Blocks FR-4." and "OQ-2: What is 'large repository' concretely, and what is the performance target beyond the 5-second success criterion?". It added four further questions (TODO syntax, test and vendor files, output form, one or many modules).
- Run 2 (spec) found gap B as an open question. It did not ask about gap A. It wrote gap A as a constraint ("measured against the success signal's 5-second budget") and an assumption ("'large' is unquantified"). So the same PSB gave a question in one skill and an assumption in another.
- Run 3 (architecture) closed four of the spec's open questions itself as `[ASSUMPTION]` entries (scan scope, error cases, empty output, stale presentation), and run 4 assumed "2,000 packages of 10 files each" for the benchmark story. The guesses are tagged, not hidden.

**S11 test (identifier, trace, acceptance criterion).**

- Identifier: yes in every artifact (`FR-N`, `CAP-N`, `AD-n`, story `id`).
- Acceptance criterion: yes (`Consequences (testable)` per FR; `success` per CAP; `verify` per story).
- Trace to the PSB sentence: not in the PRD and not in the spec file. The spec's memlog cites lines ("CAP-1 ... (PSB 3-5,12)"), but no rule asks for it. The ticket tree (run 4) gave a real trace: `covers = ["PSB-4", "PSB-14"]` and so on, because the skill makes a numbered source the requirement ids. Our PSB was already numbered and the prompt said so.
- Mechanical check of the trace: none. We changed one story to `covers = ["PSB-99"]`; `tickets.py status` exited 0 with no problem. We ran `tickets.py mark ... 7 done` on the `hitl` story; it exited 0 and wrote `status: done`, with no check of who ran it.

**Other checks.** `lint_spine.py` on a copy of the spine with every `Prevents:` line removed printed `"ok": false`, ten `high` findings, and exit status 0.

**Run 5 (unattended build).** The run wrote a plan beside `tickets.toml` with Given/When/Then acceptance criteria and an I/O matrix, moved the status through `in-review` to `built`, ran four context-free review lenses (blind-hunter, edge-case-hunter, verification-gap, intent-alignment), wrote a triage log with a verdict per finding, and committed locally. Two observations:

- The finalize rule says "Verify the version-controlled working copy is clean. Otherwise HALT with status `blocked`" ([step-04-review.md#L174](https://github.com/bmad-code-org/BMAD-METHOD/blob/ec9a46ee2aef5631ea102faa969a6db5ee296ce1/skills/bmad-build-auto/step-04-review.md#L174)). The tree was not clean: the skill's own render cache `_bmad/render/` was untracked. The agent chose to treat it as "workflow output" and ended `built`. A rule in prose bent under the LLM's judgement; code would not have bent.
- The session that wrote the code also triaged the reviewers' findings and rejected 23 of 32. The reviewers are fresh, but the verdict on their findings is not independent.

## Where the searchers were wrong or incomplete

- Searcher B, items 9 and 10 "no": item 9 is partly (a loop limit of 5 exists in `bmad-build-auto`); item 10 is no, confirmed.

- Searcher B, conflicts: "Agents can install and update skills (`npx skills update`), so Invariant 3 is not shown." Confirmed and stronger: the agent can also mark a `hitl` ticket `done`.
- Searcher B on BMAD Loop: "a different repo". Correct; the help says bmad-loop "does not dispatch from the ticket tree yet" ([unattended-builds.md#L8](https://github.com/bmad-code-org/BMAD-METHOD/blob/ec9a46ee2aef5631ea102faa969a6db5ee296ce1/skills/bmod-method/help/unattended-builds.md#L8)).

## Limits of this evaluation

- Five agent runs on one tiny PSB, one model (Claude Sonnet 5), one harness (Claude Code). The Codex and Cursor installs were checked as files only; we did not run a skill under them.
- Headless and autonomous modes only. The interactive coaching paths, party mode, `bmad-ux`, `bmad-prfaq`, `bmad-correct-course` and the tracker stores were read, not run.
- The run 4 trace depended on a PSB that was already numbered and a prompt that said so. We did not test an unnumbered PSB.
- The retrospective was read, not run, because no epic was finished.
- The main branch carries a pre-release version (6.13.0-next). Behaviour can change.
- Processes: all five `claude -p` runs ended by themselves; no server, daemon or container was started.
