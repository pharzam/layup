## Verdict

Borrow the pattern, and use one file format. Spec Kitty has the best public mechanism set of the four candidates for spec, lanes, review evidence and per-requirement acceptance, and it keeps the mission record in the project's Git. But it writes about 630 files into the user's `$HOME` on every CLI call, a forced move fabricates review evidence, its rule guard is `warn` by default, and it has no cost record and no trace to the source sentence. LAYUP cannot take it as a dependency (Python; F-0004 fact 1).

## What it is (from the code)

- **Workflow.** A mission type is a step list: discovery, specify, plan, tasks, implement, review, accept. Each step names an agent profile and a prompt template ([mission-runtime.yaml:33-80](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/packs/built-in/missions/software-dev/mission-runtime.yaml#L33)). The prompts are one canonical source per step, for example [specify/prompt.md](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/packs/built-in/missions/mission-steps/software-dev/specify/prompt.md#L1).
- **Work-package lanes.** A finite-state machine with the lanes genesis, planned, claimed, in_progress, for_review, in_review, approved, done, blocked, canceled ([status/models.py:29-68](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/models.py#L29)). Guards live in the state objects ([status/wp_state.py:300](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/wp_state.py#L300), [:410](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/wp_state.py#L410), [:435](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/wp_state.py#L435)). Approval needs a reviewer, a verdict `approved` and a reference ([wp_state.py:578-593](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/wp_state.py#L578)). A force needs only a non-empty actor and reason ([wp_state.py:190-196](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/status/wp_state.py#L190)).
- **Event log in Git.** Each transition appends to `kitty-specs/<mission>/status.events.jsonl` and makes a commit on a coordination branch `kitty/mission-<slug>`. Each work package gets a Git worktree under `.worktrees/`.
- **Requirement mapping.** Spec requirement IDs (`FR-`, `NFR-`, `C-`) are parsed by regular expressions ([requirement_mapping.py:15-72](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/requirement_mapping.py#L15)). `finalize-tasks` fails when a functional requirement maps to no work package or a work package names an unknown ID ([mission_finalize.py:1281-1283](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/cli/commands/agent/mission_finalize.py#L1281)).
- **Acceptance matrix.** One criterion row per requirement with `pass`, `fail` or `pending`, `evidence` and `verified_by`. A `pending` row gives the overall verdict `pending`, not `pass` ([acceptance/matrix.py:371-397](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/acceptance/matrix.py#L371)). An open or deferred `[NEEDS CLARIFICATION]` decision blocks acceptance ([acceptance/__init__.py:804-825](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/acceptance/__init__.py#L804)).
- **Decision Moments.** A question to the human is a record in `kitty-specs/<mission>/decisions/` plus an event. The emitter sets `actor_type` to `human` by default ([decisions/emit.py:67](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/decisions/emit.py#L67)).
- **Intake.** `spec-kitty intake FILE` copies a plan document to `.kittify/mission-brief.md` with a SHA-256 hash ([mission_brief.py:126-147](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/mission_brief.py#L126)). A structured "handoff packet v1" in YAML front matter carries requirement IDs, `source_id` and acceptance criteria, and the parser validates it ([handoff-packet-v1.md:55-91](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/docs/contracts/handoff-packet-v1.md#L55)).
- **Commit guard.** A pre-commit hook blocks writes to `kitty-specs/` from implementation branches and writes outside the work package's `owned_files` ([policy/commit_guard.py:86-113](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/policy/commit_guard.py#L86)). The default mode is `warn` ([policy/config.py:40-42](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/policy/config.py#L40)).
- **Retrospective.** A pure-Python, byte-deterministic generator reads the mission artifacts and events and writes a schema-valid `retrospective.yaml`. It must not change doctrine; proposals are data, applied only with `--apply` ([retrospective/generator.py:1-15](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/retrospective/generator.py#L1)). It detects rejection cycles, forced transitions and self-review ([generator.py:398](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/retrospective/generator.py#L398), [:680-700](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/retrospective/generator.py#L680)).
- **Invocation records.** `kitty-ops/` holds start and completion records with actor, `model_id`, `started_at`, `completed_at` and outcome, but no token count ([invocation/record.py:48-80](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/invocation/record.py#L48)).
- **Harness surfaces.** One list of 13 harness directories ([agent_utils/directories.py:16-30](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/agent_utils/directories.py#L16)). On every CLI start (not `--version`, not `session-start`) the CLI calls `ensure_runtime`, `ensure_global_agent_skills` and `ensure_global_agent_commands`, which write into `$HOME` ([src/specify_cli/__init__.py:143-152](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/__init__.py#L143); design note in [m_3_1_2_globalize_commands.py:1-18](https://github.com/spec-kitty/spec-kitty/blob/af847be71d97c8a126e91c31a7d05629c69c93ba/src/specify_cli/upgrade/migrations/m_3_1_2_globalize_commands.py#L1)).

## Where the searchers were wrong or incomplete

- Searcher B: "Spec Kitty is local-first and stores its core artifacts in your repo." True for mission artifacts. Not said: the CLI writes command and skill copies for 13 harnesses into the user's `$HOME` on any subcommand, even for harnesses not selected. This is the main risk for LAYUP.
- Searcher B, S5 "A machine schema is not stated": wrong in part. The handoff packet v1, `wps.schema.json`, the FSM guards and the retrospective schema are machine-checked.
