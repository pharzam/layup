## Operator decisions O-52 to O-59 (R7) — the answers to the panel's questions, in one batch

Asked in the Claude Code session on 2026-09-25, in two parts of four, from the questions that panel members A and B put to the Operator. Each question and answer is copied word for word; the option texts the Operator chose are quoted.

**O-52 — the runner (Q1).** Question: "Q1 (the runner, REQ-007): may LAYUP run a hosted GitHub App with a webhook endpoint that posts required check runs on a target (B's 1A, A's G1), or must the runner stay inside GitHub Actions and tokens (B's 1B: a commit status that the shared account could forge)?" The Operator chose **"A GitHub App with check runs (Recommended)"**: "The App identity signs the verdicts; a required check with no report blocks the merge by the forge's own rule; nothing of LAYUP enters the target. Needs a small hosted endpoint (or Actions in LAYUP's repo receiving the App's events)."

**O-53 — the identities (Q2, closes O-9).** Question: "Q2 (rule protection, REQ-003, O-9): will the agents get their own GitHub identity (an App or a second account), so that a CODEOWNERS review by the human account can be required on rule paths (B's 2A)? Or must the control work with one account, through a signing key the agents do not hold (B's 2B)?" The Operator chose **"Separate identities: agents get an App or account (Recommended)"**: "You keep the human account; agents push as an App or a second account; CODEOWNERS + required code-owner review on rule paths; enforce_admins on. The forge refuses an agent rule change before merge."

**O-54 — the records (Q3).** Question: "Q3 (Invariant 1 and where records live): is a verified mirror file in the target (docs/setup/branch-protection.json, checked by layup setup verify) enough for "Git is the system of record" where the control itself is a forge setting? And do gate results, handoffs, escalations and stall records live in the TARGET's runs/ (the kit rules, O-13) or in LAYUP's runs/?" The Operator chose **"Mirror file is enough; records in the target's runs/ (Recommended)"**: "The forge setting is mirrored and verified in the target's Git; every task record lives in the target (O-13: the target follows the adapted kit's rules)."

**O-55 — the roles (Q4).** Question: "Q4 (the roles, REQ-005; the PSB sets none, F-0001#21): which role list does LAYUP start with?" The Operator chose **"The kit's gate roles: planner, implementer, reviewer, examiner, operator (Recommended)"**: "B's 3A: the roles are the kit's own steps, so the handoff records are the plan, the review record, the verdict, the stall record; validated by the kit's linters plus a handoffs.tsv transition table. Fewest new concepts."

**O-56 — the escalation rule (Q5).** Question: "Q5 (the escalation rule, REQ-008): the panel offers a deterministic floor (B's 4A / A's E2: the approved-intent files and recorded bounds are read; a change to them or a proposal outside a bound escalates) and a declared ceiling (A's E1 / B's 4B: each decision record carries a class on four axes; the engine stops on a business-forking class; a second model audits). Which form?" The Operator chose **"Both, stacked: deterministic floor plus declared class (Recommended)"**: "The floor catches every change to the approved-intent files and any proposal outside a recorded bound without a model call; the declaration catches a fork that no file shows; a rejected declaration counts as unplanned input (F-0001#28)."

**O-57 — the intent files (Q6).** Question: "Q6 (the approved intent and the budget): which files hold the approved intent and the funding limit that the escalation floor reads? Today: the PSB (F-0001, F-0003), PRD-0001's scope and priorities, and no budget file." The Operator chose **"The PSB facts, the PRD, and a new budget record you write (Recommended)"**: "docs/facts/F-000N (the PSB), docs/prd/PRD-0001 (scope, MoSCoW, phases), and docs/setup/budget.md that you set before the pilot (token and money limits per requirement or per task); a change to any of them is a fork."

**O-58 — the stall limits (Q7).** Question: "Q7 (the stall limits, REQ-010; Invariant 4 says these are yours to set, not guessed): the retry count N of identical-input attempts, the no-progress time T, and the disagreement rule. Which start values does the pilot use?" The Operator wrote: **"1, but 15min, minutes without a recorded progress event stops the step; a review disagreement is a stall when the cycle cap is reached with a material finding open. The pilot measures and you reset them in one batch."** Read as: N = 1 identical-input retry (the second identical attempt stops the step), T = 15 minutes without a recorded progress event, and the disagreement rule as offered; the pilot measures both and the Operator resets them in one batch.

**O-59 — the examiner (Q8).** Question: "Q8 (the examiner of a stall): a fresh session that did none of the stalled work, on a different harness or model where one is available. When no second harness is available, may the examiner be a fresh session on the same harness with a different model, recorded as such?" The Operator chose **"Yes: fresh session, different model; same harness allowed and recorded (Recommended)"**: "The independence test is the one of Who may review (Context, Execution, Model); the record names the levels not reached."

These decisions are inputs for ADR-0013 to ADR-0017 and are copied into Git by them. Member A's question on whether "reaches human review" (REQ-007) means a managed review queue is answered by O-52's mechanism: the required check blocks the merge; review assignment is the target's own rule, and the pilot audits early reviews.


## Operator decisions O-60 to O-62 (R7) — member C's questions

Asked in the session on 2026-09-25 after panel member C's output; copied word for word.

**O-60 — the O-10/O-11 scope.** Question: "Member C's question 2 (O-10/O-11 scope): does a forge setting on a target (branch protection, required checks, a ruleset) or a CODEOWNERS file in the target count as "writing LAYUP into the target"? O-11 allows the kit copy and the facts only." The Operator chose **"Yes: only the kit copy and the facts; no CODEOWNERS"**, whose text was: "Rule protection must then come from LAYUP's App check alone (B's 2B), which needs O-53's identities anyway." Read with the kit's own setup step S13 (`docs/setup/steps.tsv`), which writes the target's branch-protection body as a kit record: the required checks stay a kit record of the target; no `CODEOWNERS` file is written, and the control is the App's check.

**O-61 — rule-change approval.** Question: "Member C's question 5: is an approval of a rule-path change in a target a planned approval point (Decision Point 3, recorded before delivery; it does not count as unplanned input) or unplanned human input (F-0001#28)?" The Operator chose **"A planned approval point, recorded before delivery (Recommended)"**: "The target's setup record names "a change to a rule path" as a planned approval point whose approver is the Operator; each approval is counted, not as an intervention."

**O-62 — the escalation triggers.** Question: "Member C's question 6: the escalation trigger list (the intent paths and the bounds the deterministic floor reads) defines "approved intent". Must the idea owner approve it before delivery, and which error direction is accepted when the rule is unsure?" The Operator chose **"The idea owner approves the list; when unsure, escalate (Recommended)"**: "The trigger list is part of the pilot's PDR that you accept (Decision Point 1); an `unknown` classification stops and escalates; the cost is counted as unplanned input when you do not confirm it."

Member C's other questions are answered by O-52 (a network service for the runner, not the engine), O-53 (the identity split), O-54 (where the verdict lives: the target's `runs/`, mirrored forge settings), O-58 (the stall limits, as marked hypotheses) and O-59 (the examiner).
