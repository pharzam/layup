## What was done

1. **`task-state.sh`:** `forge/issues` (the number and the title of each open issue) is
   a required input. An open issue whose title starts with a task ID and a colon is a
   task when no row of the plan, no line of `## Now` and no line of the completed log
   names that ID or that issue; of two such issues the lower number is the task. It takes
   the states of any task: `ready` with no branch, `in progress` or `stalled` with the
   branch, `in review` with an open pull request. `--prs FILE` writes the table of the
   open pull requests, `NUMBER TAB HEAD TAB ISSUES`, the issues that each body closes (no
   third field when none): the one parser of the closing keywords.
2. **`task-labels.sh`:** its header is the one home of the rule. The reader takes the
   table `prs` and gives each open issue exactly one `state:` label: a task issue the
   state of `task-state.sh`, any other open issue `state: in review` when a row of `prs`
   names it and `state: on hold` when none does, and a closed issue `merged` or
   `rejected` by its close reason, also when it is no task issue and still carries a
   `state:` label (a closed issue that never had one stays as it is). The applier runs
   `task-state.sh --prs`, and makes eight labels, `state: on hold` the new one, each
   described as set by the workflow alone.
3. **The fixtures:** 11 new cases and 2 changed, 57 in all, and a base with `forge/issues`
   and `prs`: the title tasks (no branch, a branch with activity, a branch with none, named
   twice, named by a row of the plan or a line of the backlog under another number), the
   table of `--prs`, the open issues outside the set (no pull request, each closing keyword,
   one that only refers, already right, a wrong label), the closed issues (with a stale
   label, with none), and the missing inputs.
4. **The workflow `task-state.yml`:** its header comment only; no trigger, no permission,
   no step.
5. **The documents:** `AGENTS.md`, Starting a task in `docs/engineering-discipline.md`,
   `docs/ci/README.md`, the glossary and the README of the cases say who gets which label
   in one sentence each and link to the header of `task-labels.sh`; the pitfall of
   `git diff --check` in `guardrails.md` §2 gains the case of this task.

**Tests:** [`test-runs.md`](../../runs/T-j304/test-runs.md): 12 of the 57 cases red before
