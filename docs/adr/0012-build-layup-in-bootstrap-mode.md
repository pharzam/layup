Five root causes, with the evidence in the diagnosis (the fifth was shown by this record's own review rounds):

1. **Process about process.** The routing policy (`F-0005`, then the revised text of 2026-09-25) says which model reviews which comment while agents build this repository. It does not describe LAYUP, and ADR-0011 decision 8 says the engine makes no model call. A day of work and 26 decision numbers (19 decided, 7 open) went to a rule that changes no product line.
2. **The gate multiplies a small task, and one rule is unstable.** A 356-line text file needs an issue, a sliced plan, an independent plan review, red and green runs, a frozen head, two review rounds with a different model, a resource record and a verdict: at least four model sessions. The R11 goal-class count gave three answers for the same task shape (1 for `F-0005`; "at least 6" and "at least 4" for its successor), so a plan can be rejected without limit. That is the PSB's Problem 4, a deadlock with no state and no limit, reproduced inside the process.
3. **The gate depends on external services at review time.** 18 external runs failed; each failure cost an Operator decision (O-27, O-29, O-30, O-31, O-39, O-40), which is the PSB's Problem 1, the human as message bus.
4. **The kit is applied in the wrong phase.** Armature is a discipline for a team that delivers a specified product. LAYUP has no PRD and no pilot, and the machinery that LAYUP must automate (panels, routing, stall packages) is run by hand on LAYUP itself, before LAYUP exists. The product path is short and open: #45 (the idea owner answers 19 gap questions), #42 (the PRD), #29 (`layup setup`).
5. **The review loop.** The rules are prose, restated in six documents; "material" was read as any claim a reader could act on; each fresh reviewer returned 5 to 13 findings on that prose, whichever model reviewed; and the cycle cap then split the issue into a successor instead of converging it. The task that wrote this record met the same loop: an approved plan, 13 findings in round 1, `not mergeable, findings recorded` at the cap in round 2, and a successor (#56 → #59). Rules 3 and 7 of the operative section are the answer: a finding is material by a stated test and a note causes no round, and a rule has one home.

The process had also started to lose its own state: three reviewer records on #46 were never posted; O-15 names two different decisions; `docs/tasks/backlog.md` on `main` was empty with six tasks open; no resource record exists for #46, #53 or #54.

## Decision

We will **build LAYUP in bootstrap mode** until the ADR that supersedes this record is accepted, after the first pilot. Bootstrap mode is one decision with six parts. The operative text lives in [`engineering-discipline.md` § Bootstrap mode](../engineering-discipline.md#bootstrap-mode); this record says why.

1. **Scope.** A task in this repository is one of: a PSB In-Scope item (`F-0003#41`–`#52`) or a child of one; a defect that blocks such a task; a documentation fix that a task leaves stale. No new process rule, routing rule, check script or policy capture starts unless a product task needs it and its plan names the In-Scope fact it serves.
2. **The gate.** Issue first, a short plan, red then green, a frozen head, evidence under `runs/`, a resource record and a close-out stay as they are. Three parts are read with a substitution: the plan review is **one comment** by the Operator or by one fresh agent session, and a `reject` on the goal count alone is decided by the Operator, whose count is final; the review runs **one round** by a fresh session whose model differs from the author's, and a second round only after a fix, with a cycle cap of 1, or 2 when the change touches a gate; a **panel** is convened only for an ADR that changes the product architecture. Two rules bound the rounds: a finding is material by the test in rule 3 of the operative section, and every other finding is a note that causes no round; an operative rule has one canonical home, and another document may only link to it or give a clearly marked non-operative summary (rule 7). `review-record-lint`, the hooks, branch protection and CI do not change.
3. **Routing, the whole rule.** The author is the model whose session wrote the change under review: Claude Opus 5.5 on Claude Code unless the task's issue names another model of the reasoning tier, and where more than one model wrote the change, each is an author. A reviewer is any model that differs from every author's, on `claude`, `devin` or `opencode`, tried one at a time in the order the author names on the issue, until one returns a record; a harness that fails, gives no output within five minutes, or gives no record within fifteen, is skipped and named in the resource record, and no decision is asked for it. The tiers of ADR-0005 get names: reasoning — Claude Opus 5.5, Claude Fable 5.1, GPT-6 Sol, Grok 4.7; execution — Claude Sonnet 5, SWE-2, GPT-6 Luna. Not used: the models the Operator listed as not to use (the evidence file, §14: GPT-4.1, GPT-5.1, 5.2, 5.4; Opus 4.5 to 4.8; Opus 5 — the same text names `claude-opus-5-5` in every Claude row, so this record reads "Opus 5" as the model of that name and not as Opus 5.5; Sonnet 4.5 and 4.6; Haiku; deprecated models; `-fast` and `-priority` variants; `adaptive`; paid Zen models while that account has no funds; DeepSeek on OpenCode Go while its region restriction blocks it). Nothing else is routed, and no quota state is tracked.
4. **The routing line ends.** The merge of PR #50 is reverted by one revert commit (no history is rewritten), so the tree holds no `F-0005`. The Operator's revised routing text of 2026-09-25 (356 lines, SHA-256 `60d05d35ecd58922c3bade2dc4cd8ec9a2a6d2a698612899d943ab937c99be7f`, attested on #55 under O-37) is kept as evidence at [`runs/T-8ywj/operator-routing-answer.md`](../../runs/T-8ywj/operator-routing-answer.md); it is not a fact and no ADR assesses it clause by clause. The draft ADR-0012 on branch `T-7wqc` (`30ca13f`) is not merged and is kept under the tag `archive/adr-0012-draft`. Issues #54, #51, #52 and #55 close as not needed before the pilot; #49 (the R11 count) waits for the end of bootstrap mode. The number 0012 is taken by this record on purpose: `F-0005`'s record said that ADR-0012 would assess it, and ADR-0012 now says why it does not.
5. **The product path, in order.** #45: "The author drafts all 19 answers for #45. The idea owner accepts or edits every answer explicitly in one batch before the answers become operative." (O-43; the batch is Decision Point 2, `F-0001#11`, and the accepted answers are `F-0004`.) #42: `PRD-0001`, one requirement per In-Scope item, each traced to `F-0003#41`–`#52` with an acceptance criterion. #29: `layup setup` (a target from `setup/steps.tsv`), `layup gate` (the kit's checks run from outside a target), the telemetry record, the stall record. Each deliverable named here — the #45 batch, `PRD-0001`, `layup setup`, `layup gate`, the telemetry record, the stall record — is one task under part 2; #29 stays their parent issue.
6. **When the mode ends.** The mode ends when the ADR that supersedes this record is accepted, and not before. The first pilot is done when `layup` has set up one target repository from a problem statement and has run that target's gate from outside (ADR-0011 decisions 3 and 4); the task that closes the pilot opens that ADR, which re-decides the full gate with the pilot's numbers and sets this record's Status to `Superseded`.

We rejected, so that none is reopened without new information: **finish the draft ADR-0012** — 1,416 lines keyed to `F-0005` line numbers, seven open decisions (O-19 to O-25), two open findings, and an input (`F-0005`) that the Operator's own revised text declares incomplete; **keep the full gate and close only the routing line** — the next document task meets the same R11 deadlock and the same external-service failures; **drop the gate** — breaks Invariants 3, 5 and 6 and the PSB's own success criteria; **keep `F-0005` and mark it withdrawn** — sound, and the Operator chose the revert instead, for a tree with no routing fact.

## Consequences

- Product work starts on #45 within a day of the merge, under a gate of one plan-review comment and one review round. What was cut is written here, so nothing is lost silently.
- Fewer review rounds find fewer defects. That risk is accepted for the bootstrap phase and measured by the pilot: the ADR that ends this mode (part 6) reads the pilot's defect and stall numbers before it restores or re-decides the full gate.
- The revert deletes the raw fact `F-0005`, its checks, the task file `T-q1x6.md` and its completed-log line from the tree; Git history keeps them all, with PR #50. The completed-log line of this task names the revert. The Operator's revised text stays in Git as evidence (Invariant 1), with its hash in this record.
- ADR-0005's Status becomes `Accepted. Amended by ADR-0007 and ADR-0012` (its tiers get names, and its independence bound stays); ADR-0006's Status becomes `Accepted. Amended by ADR-0012` (a panel only for a product-architecture ADR). Nothing else in either record changes.
- Nothing new is mechanized. `review-record-lint` still parses the plan, its review and the rounds; no check reads which model ran, as ADR-0005 already states.
- The documentation issues #15, #21, #24, #34 and #48 stay open as documentation fixes under part 1; they are batched into product tasks that touch the same files.
